## 2. GPU 核心架构与计算参数

### 2.1 计算单元组织（本地实测）

`macainfo` 直接读出 C550 的计算资源层次结构。沐曦自研架构的分层术语如下（首次出现标注中英对照）：

- 数据处理器簇（Data Processor Cluster，DPC）：**8 个**，每簇含 1 个 DPC Array
- 加速处理器（Accelerator Processor，AP）：**104 个**，即每个 DPC 含 13 个 AP
- 处理单元（Processing Element，PEU）：每 AP 含 **4 个** PEU，全片共 416 个

### 2.2 线程模型：Wavefront 详解与 NVIDIA 对比

本机 `macainfo` 显示 Wavefront Size 为 64，这是理解 C550 性能的关键概念。下面从编程模型、硬件执行层次两个视角解释 Wavefront，再与 NVIDIA 的线程模型逐项对比。

#### 编程模型：写代码时看不到 Wavefront

MUSA 的编程模型与 CUDA 完全一致，用户可见的线程层次只有三级：

- 线程（Thread）：最小编程单位
- 线程块（Thread Block）：一组线程，共享内存，可通过屏障同步
- 网格（Grid）：一次内核（Kernel）启动包含的全部线程块

内置变量 `threadIdx / blockIdx / blockDim / gridDim` 与 `<<<grid, block>>>` 启动语法都沿用 CUDA（见 03-MUSA编程.md）。**Wavefront 不是编程模型概念，而是硬件执行层面的调度单位**——写内核时无需、也无法直接控制它。

#### 硬件执行层次：四级映射

沐曦官方把软件层次与硬件层次一一对应（官方《MXMACA 性能调优指南》C500 章节，C550 同架构适用）：

| 软件层次 | 硬件层次 | 说明 |
|---|---|---|
| Grid | GPU | 一次内核启动对应整颗 GPU |
| Thread Block | AP（加速处理器） | 一个线程块驻留在一个 AP 上执行 |
| Wave（Wavefront） | PEU（4 × 16 Lane） | 64 线程，最小调度单元 |
| Thread | Lane | 单线程的运算通路，含独立寄存器 |

对应本机实测数字：

- 全片 104 个 AP，每 AP 4 个 PEU，每个 PEU 16 个 Lane → 4 × 16 = 64 Lane，恰好承载一个 64 线程的 Wavefront
- 每 AP 最多驻留 32 个 Wavefront = 2048 线程（实测 Max Waves Per AP = 32、Max Work-items Per AP = 2048）
- 每个线程块最大 1024 线程（实测 Workgroup Max Size），即最多 16 个 Wavefront

#### 什么是 Wavefront

Wavefront（线程束，macainfo 中记作 Wavefront Size，官方文档亦写作 wave 或 warp）是 GPU 上任务调度的最小单元：**64 个线程按锁步（lockstep）方式执行同一条指令，各自处理不同数据**。类似 CPU 的 SIMD 向量化，但规模更大，由硬件调度器管理。

关键特征：

- **单指令多线程（Single Instruction, Multiple Threads，SIMT）**：束内所有线程同时取指、执行同一条指令，只是操作数不同
- **锁步执行**：束内线程进度一致，共享控制流
- **束是资源分配粒度**：寄存器、共享内存、调度槽位都以束为单位占用

命名说明：macainfo 输出用「Wavefront」，沐曦官方文档多称「wave」。官方文档提到「公司内很多文档跟随 AMD 管理使用 wave 一词」——wave 是 AMD 的术语习惯，warp 是 NVIDIA 的术语习惯，沐曦文档中两者混用，指的都是同一个东西。

#### 执行方式：与 AMD 的异同

从数字上看，沐曦的 AP（4 PEU × 16 Lane = 64 Lane）与 AMD GCN 架构的计算单元（Compute Unit，CU，4 SIMD × 16 Lane = 64 Lane）几乎相同，容易误以为执行方式也相同。实际有本质区别：

| | 沐曦 C550 | AMD GCN |
|---|---|---|
| 64 线程的束如何执行 | 4 个 PEU 共享同一指令发射源，束整体由 AP 的 64 Lane 宽度承载 | 拆成 4 个 16 线程的 quarter-wavefront，分发到 4 个独立 SIMD，各自取指执行 |
| 指令发射 | AP 内发射单元把驻留的束分成 4 组，每周期按 PEU0 → PEU3 顺序从各组选一条指令发射 | 每个 SIMD 独立取指、独立发射 |

换句话说：沐曦的 4 个 PEU 是同一发射器的 4 个服务目标，AMD 的 4 个 SIMD 是 4 个独立的小处理器。沐曦官方将自身架构描述为自研 XCORE，未声明与 AMD 存在血缘关系。

#### 与 NVIDIA 线程模型对比

NVIDIA 的模型以 warp（线程束）为核心：**32 个线程**为最小调度单位，一个 warp 由一个 warp scheduler 调度，在 SM（流式多处理器）上执行。逐项对比：

| 概念 | 沐曦 C550 | NVIDIA（A100 / H100） |
|---|---|---|
| 束大小 | 64 线程（Wavefront / wave） | 32 线程（warp） |
| 处理器 | AP，全片 104 个 | SM，A100 有 108 个 / H100 有 132 个 |
| 每处理器驻留 | 32 束 / 2048 线程 | A100 每 SM 64 束 / 2048 线程 |
| 束内执行 | 锁步，束内共享控制流 | SIMT：同地址启动、各线程独立 PC 与寄存器；Volta 起支持独立线程调度 |
| 分支分歧 | 官方确认束内存在分歧，恢复机制未公开 | 束依次执行每个分支路径，屏蔽不在路径上的线程 |
| 块内同步 | `__sync_threads()`（即 `__syncthreads`） | `__syncthreads()` |
| 束级同步 | `__sync_wave()` | `__syncwarp()` |
| 共享内存 | WSM 64 KB / AP | A100 每 SM 164 KB（可配置） |
| 发射单元 | 每 AP 1 个发射单元，轮询 4 组 | 每 SM 4 个 warp scheduler（CC 7.x / 8.x），并行发射 4 条指令 |

要点解读：

- **束大小差异（64 vs 32）的影响**：束越大，单条指令覆盖的数据越多，内存带宽利用率越高；但分支分歧时浪费也越大——同一束内只要有一个线程走另一分支，整个束就要串行执行两个路径。block 大小取 64 的倍数可获得最优利用（官方建议）。
- **SIMT 模型相同**：两种 GPU 都是 SIMT，束内线程从同一程序地址启动，各有独立寄存器状态。
- **同步语义相同**：`__sync_threads()` 对应 `__syncthreads()`，都是线程块级屏障；`__sync_wave()` 对应 `__syncwarp()`，都是束级屏障。

#### 分支分歧与性能建议

**分支分歧（Control Divergence）**：当束内线程因数据不同而走不同分支（如 `if (i % 2)`），硬件只能依次执行各分支路径，束的执行时间变成各路径之和。优化方向是让束内线程尽量走同一路径，或将分歧移到束边界。

沐曦官方性能调优指南给出以下对齐建议（C500 章节，C550 同架构适用）：

- block 大小取 64 的倍数（对齐 waveSize）
- 每 AP 至少 8 个活跃束（256 线程），即 25% 占用率起步
- 计算密集任务：每 AP 活跃束 ≥ 4 个；访存密集任务：block 数 ≥ 64
- grid 维度取 AP 数（104）的整数倍，避免尾部效应（Tail Effect）
- 用 `__launch_bounds__` 限制 block 大小，提升占用率

#### 资料来源说明

本节架构细节主要来自沐曦官方《MXMACA 性能调优指南》《MXMACA C++ 编程指南》《运行时 API 编程指南》中对 C500 芯片架构的描述。C550 与 C500 同代同架构（XCORE），且本机 `macainfo` 实测的 C550 数字（104 AP、4 PEU、64 束、32 束/AP）与官方 C500 文档完全一致，故可直接适用。NVIDIA 侧依据 CUDA C Programming Guide。

### 2.3 计算单元内部架构与存储层次

本节展开 AP（加速处理器）内部的计算单元构成、指令发射、寄存器堆与存储层次细节，并与 NVIDIA SM（流式多处理器）逐项对照。以下架构细节来自沐曦官方《MXMACA 性能调优指南》C500 芯片架构章节与《MXMACA C++ 编程指南》，本机 C550 实测数字与官方 C500 文档一致，可直接适用。

#### 2.3.1 AP 内部执行单元

一个 AP 内含三类执行单元，各司其职：

| 执行单元 | 缩写 | 职责 | 对应 CUDA 概念 |
|---|---|---|---|
| 标量执行单元 | STE | 执行标量指令（`sadd_u32`、标量加载 `ldu_b32`），处理 blockIdx 等束内统一数据与控制流 | 标量/统一数据通路 |
| 向量执行单元 | MTE | 由 4 个 PEU 组成，执行向量指令（`fma_f32`、向量加载 `ldg_b32`、共享内存访问 `lds_b32`），共 64 lane | CUDA Core（FP32/INT 通路） |
| 矩阵执行单元 | MMA | 执行矩阵指令，如半精度 `MMA_16x16x16F16` | Tensor Core |

每 AP 64 lane（4 PEU × 16 lane），与一个 64 线程 Wavefront 的硬件宽度对应。

#### 2.3.2 指令发射宽度

AP 内单个指令发射单元负责全部 warp 调度：

- 驻留的 warp 被分成 4 组，每组对应 1 个 PEU
- 每个时钟周期，发射单元按 PEU0 → PEU3 顺序，从各组活跃 warp 中选择指令发射
- 每周期最多发射 **5 条指令**：1 标量（ALU 或标量访存）+ 1 矩阵或向量 ALU + 1 向量访存 + 1 共享内存 + 1 杂项（MISC）

对比：NVIDIA SM（Ampere/Hopper）每周期由 4 个 warp scheduler 各发 1 条，共 4 条；C500/C550 是「1 个发射器、5 个发射口」。

#### 2.3.3 寄存器堆

| 项目 | 数值 | 与 NVIDIA 对比（A100） |
|---|---|---|
| 向量寄存器（mtreg） | 每 AP 64 lane × 2048 个 32-bit 寄存器 = **512 KB** | A100 每 SM 256 KB，沐曦为 2 倍 |
| 每线程最大向量寄存器 | 256 个 32-bit | A100 每线程 255 个 |
| 标量寄存器（streg） | 每 AP 800 个 32-bit | A100 无对应概念 |
| 分配粒度 | 以 warp（64 线程）为单位 | 以 warp（32 线程）为单位 |
| 溢出（spill） | 溢出变量进入 Private Memory（片外全局内存），汇编表现为 `stp` / `ldp`，成本与全局内存相当 | 溢出到 local memory，同样在片外 |

编译器控制：`mxcc` 支持 `--maxrregcount`（限制向量寄存器）与 `--maxsregcount`（限制标量寄存器）；`__launch_bounds__` 可约束寄存器用量以提升占用率。大结构体传参与动态索引数组最容易引发 spill。

#### 2.3.4 存储层次

实测缓存容量（`macainfo`）+ 官方架构细节：

| 层次             | 容量          | 访问延迟       | 说明                                     |
| -------------- | ----------- | ---------- | -------------------------------------- |
| 寄存器堆           | 512 KB / AP | 1–4 ns     | 见 2.3.3                                |
| 共享内存（WSM）      | 64 KB / AP  | 约 60 cycle | 可编程，`__shared__`，见 2.3.6               |
| Vector L1（VL1） | 32 KB / AP  | 约 60 cycle | 缓存全局内存数据，**默认关闭**                      |
| 标量 L1（SL1）     | 未公开         | —          | 缓存标量数据，驱动可单独刷新                         |
| 常量 L1          | 8 KB / AP   | 约 12 ns    | `__constant__` 数据，`ldu` 指令访问           |
| L2             | 8 MB（全片共享）  | 约 200 ns   | 统一缓存，128 B cacheline，实测带宽 4096 B/cycle |
| HBM2e          | 64 GB       | 400 ns 以上  | 全局内存                                   |

三个关键点：

1. **VL1 默认关闭**：官方明确 C500 默认关闭 Vector L1，所有 `ldg` 事务直达 L2。想利用 L1 数据复用须先确认 VL1 已开启，否则 128 B cacheline 内数据无法跨指令复用。
2. **L1 与共享内存分离**：WSM 是独立 SRAM，不从 L1 划扣容量（类似 AMD 的 LDS 设计，而非 NVIDIA 的「L1/共享内存统一可配置」）。`mcDeviceSetCacheConfig` 文档措辞也印证 C500 属于「L1 与共享内存容量固定」的设备。
3. **L2 为全片统一缓存**：所有 AP 共享 8 MB L2，cacheline 128 B；跨 kernel 的数据一致性依赖启动时的缓存刷新（`MACA_LAUNCH_MODE` 环境变量可配置跳过 L2 / VL1 / SL1 刷新以换取性能）。

#### 2.3.5 与 NVIDIA SM 逐项对比

| 概念         | 沐曦 C550（AP）                           | NVIDIA A100（SM）                        |
| ---------- | ------------------------------------- | -------------------------------------- |
| 线程束大小      | 64 线程                                 | 32 线程                                  |
| 执行单元       | 标量 + 向量（4 PEU × 16 lane）+ 矩阵          | 4 组 FP32/INT 单元（128 lane）+ Tensor Core |
| 指令发射       | 1 个发射器，每周期最多 5 条                      | 4 个 warp scheduler，每周期 4 条             |
| 寄存器堆       | 512 KB / AP                           | 256 KB / SM                            |
| 共享内存       | 64 KB / AP（独立 SRAM）                   | 164 KB / SM（与 L1 统一可配置）                |
| L1 Cache   | VL1 32 KB + SL1 + 常量 L1 8 KB（默认关 VL1） | 与共享内存统一（可配置比例）                         |
| L2 Cache   | 8 MB 全片统一                             | 40 MB（A100）                            |
| 每处理器驻留     | 32 warp / 2048 线程                     | 64 warp / 2048 线程                      |
| 每 block 上限 | 1024 线程                               | 1024 线程                                |

对应关系：**AP ↔ SM**（`multiProcessorCount` 字段语义一致，官方多处对照使用）；PEU 对应 SM 内的执行分区（warp scheduler 服务的执行组）。

#### 2.3.6 共享内存（WSM）细节

- **编程支持**：`__shared__` 完全支持（含 `extern __shared__` 动态分配），块内线程共享，块生命周期内存在，官方 samples 的 `0_Introduction/sharedMemory` 即分块矩阵乘示例
- **容量**：64 KB / AP
- **bank 结构**：官方原文「连续的 4-bytes 被分配到连续的 **32 个 bank** 中」，即 32 bank × 4 B，与 NVIDIA 一致
- **带宽**：无 bank 冲突时 128 B/cycle/AP（读、写各 128 B，全双工）；2-way 冲突降至 32 B/cycle；广播（同地址多线程访问）不冲突
- **与 NVIDIA 的关键差异**：C550 的 warp 是 64 线程，bank 只有 32 个，因此一个 64 线程 warp 的 32-bit 访问要分**两个阶段**完成（每阶段 32 线程）；64-bit 分四阶段、128-bit 分八阶段
- **bank 冲突优化（官方建议）**：padding（+1 列）与 swizzle（异或重排）；避免 half/char 窄宽度访问；奇数 stride 永不冲突；注意 padding 会增加 WSM 用量、降低占用率

#### 2.3.7 全局内存访问路径

官方描述的 `ldg`（全局加载）完整流程：

1. 发射单元发射 `ldg` 指令（一个 64 线程 warp 生成 64 个地址）
2. 地址进入 Vector L1，每 16 个线程聚合为一笔 **128 B transaction**（一个 warp 的连续访问合并为 4 笔）
3. VL1 命中直接返回；未命中（或 VL1 默认关闭）发往 L2
4. L2 命中返回；未命中发往内存控制器（MC），MC 访问 DRAM 取数并回填 L2 → L1
5. 数据写回向量寄存器堆，访存计数（gvm_count）递减，发射单元据此等待访存完成

要点：

- **合并访问（Coalescing）**：128 B cacheline 是访存的基本单位，束内线程连续访问才能合并，官方建议 warp 内连续 + 128 B 对齐
- **异步访存**：支持直接从 L2 加载到共享内存（`memcpy_async`，对应 CUDA 的 cp.async）
- **缓存提示指令**：`__ldg`（只读缓存）、`__ldcg / __ldca / __ldcs / __ldlu / __ldcv`（加载提示）、`__stwb / __stcg / __stcs / __stwt`（存储提示），语义对齐 CUDA
- **常量内存**：`__constant__` 支持，硬件实现为每 AP 8 KB 常量 L1，`ldu` 指令访问，须启动前由 host 设置

#### 2.3.8 与 AMD LDS 的对照

沐曦的 WSM 在设计上与 AMD 的 LDS（Local Data Share，本地数据共享）高度同构，本节补充 AMD LDS 的基本设计作为参照（AMD 侧依据 AMD GCN/CDNA ISA 手册与 ROCm 文档）：

| 项目 | AMD LDS | 沐曦 WSM |
|---|---|---|
| 定位 | 每 CU 内软件管理的片上 scratchpad SRAM，紧邻 ALU | 每 AP 内软件管理的片上 SRAM（`__shared__`） |
| 容量 | GCN/CDNA 均为 64 KB / CU（RDNA 为 WGP 128 KB = 2 × 64 KB） | 64 KB / AP |
| bank 结构 | 32 bank × 4 B（每 bank 512 entries） | 32 bank × 4 B |
| 带宽 | 32 × 32-bit = 128 B/cycle/CU | 128 B/cycle/AP（读、写各 128 B） |
| 与 L1 关系 | 独立 SRAM，与 per-CU vector L1 分离，不做 tag/状态检查（是 RAM 不是缓存） | 独立 SRAM，与 VL1 分离（详见 2.3.4） |
| 访问指令 | `ds_*` 族（`DS_READ_B32` / `DS_WRITE_B64` 等）+ `s_barrier` 同步 | 共享内存指令 + `__sync_threads()` |
| 冲突行为 | 同 bank 并发访问被硬件串行化；无冲突 1–2 cycle 完成，全冲突最多 64 cycles | 2-way 冲突带宽降至 32 B/cycle |
| wavefront 分阶段 | 64 线程 wavefront 访问 32 bank → 分低半/高半两次发出，每次 32 lane | 64 线程 warp 访问 32 bank → 分两个阶段（详见 2.3.6） |

关键理解：

- **LDS/WSM 是「RAM」不是「缓存」**：确定性可寻址、无需 tag 比较与替换策略，这是延迟低、可预测的根本原因。AMD 与沐曦的共享内存都是独立的软件管理硬件，与 NVIDIA「L1/共享内存统一可配置」的设计路线相反。
- **AMD 侧还有 GDS（Global Data Share）**：全 GPU 共享的单块小容量 SRAM（GCN 64 KB，128 B/cycle），用于跨 CU 通信；CDNA2 起移除。沐曦侧是否有对应硬件未在官方文档中见到，❌ 未公布。
- **LDS 与矩阵单元的关系（CDNA）**：AMD 矩阵指令（`v_mfma`）的操作数来自向量寄存器堆（VGPR），LDS 在矩阵乘流水里扮演 tile 缓冲——典型路径为 LDS → VGPR → MFMA。沐曦 WSM 在矩阵乘中扮演同样的 staging 角色（见 2.3.9）。

#### 2.3.9 矩阵执行单元：是否存在「Tensor Core 与 CUDA Core 分离」

**结论：存在——而且是明确的物理执行单元分离，与 NVIDIA Tensor Core、AMD Matrix Core 同构。但「分离」要分两个层面看，沐曦与 NVIDIA 的差异恰恰在指令发射层面。**

**层面一：物理执行单元——三家都是分离的**

沐曦官方文档明确 AP 内有三类并列的独立执行单元（官方原文：「每个 AP 有三种执行单元：标量执行单元，向量执行单元和矩阵执行单元」）：

| 执行单元 | 职责 | 对标 |
|---|---|---|
| 标量执行单元（STE） | 标量指令、控制流 | 控制流/统一数据通路 |
| 向量执行单元（MTE，4 PEU × 16 lane） | `fma_f32` 等向量指令 | CUDA Core |
| **矩阵执行单元（MMA）** | `MMA_16x16x16F16` 等矩阵指令 | **Tensor Core** |

**层面二：指令发射——沐曦与 NVIDIA 的关键差异**

沐曦的发射规则（每周期最多 5 条）：

```
1 条标量（STE）
1 条 MMA 或 1 条向量 ALU（MTE）     ← 互斥，共用同一发射槽
1 条向量访存（ldg/stg）
1 条共享内存访存（lds）
1 条杂项（MISC）
```

NVIDIA 的 SM 是 4 个 warp scheduler、每周期各发 1 条，Tensor Core 指令（`mma.sync` / WMMA）与普通指令**共用调度器槽位**，没有「MMA 专用发射口」概念。

| | 物理执行单元 | 指令发射 |
|---|---|---|
| NVIDIA | Tensor Core 与 CUDA Core 分离 | 4 个 warp scheduler 通用槽，无专用发射口 |
| AMD CDNA | Matrix Core 与 4×SIMD 分离 | 各 SIMD 调度器发出 `v_mfma` |
| **沐曦 C550** | **矩阵执行单元与向量执行单元分离** | **显式「1 MMA 或 1 vector ALU」共槽互斥** |

核心结论：**分离执行单元 ≠ 分离发射端口**。三家矩阵单元都是物理分离硬件，矩阵指令都走与向量指令共用的发射流水，只是沐曦把两者的互斥关系明确写进了架构文档。

实际意义：

- 同一 AP 同一周期**不能同时发射** MMA 与向量 ALU 指令
- 但 MMA 可与向量访存（ldg）、共享内存访存（lds）**同周期发射**——这是 GEMM / FlashAttention 类内核用共享内存双缓冲隐藏访存延迟的硬件依据

**层面三：软件与指令形态（与 CUDA 高度兼容）**

- **WMMA API 与 CUDA 一一对应**：`wmma` 命名空间（`fragment` / `load_matrix_sync` / `mma_sync` / `fill_fragment`），官方 microbenchmark 直接用 `nvcuda::wmma::mma_sync` 在 A100 与 C500 双平台测试
- **硬件指令形态**：`MMA_16x16x16F16`（16×16 输出、K=16 归约、FP16 输入），形状与 NVIDIA HMMA.16x16x16 相同；WMMA 支持 half 16×16×16 / 32×8×16 / 8×32×16、tf32 16×16×8、int8/uint8→int32、bf16、双精度
- **编译器内建**：`__builtin_mxc_mma_16x16x16f16`（TileLang metax 后端发射的底层形式）即硬件矩阵指令的 mxcc 内建，命名与官方 `MMA_16x16x16F16` 一一对应
- **操作数路径**：与 AMD 相同——矩阵操作数来自寄存器（mtreg，fragment），共享内存做 staging，累加器在寄存器
- **软件栈证据**：官方明确「HGEMM 和 FP8GEMM 需要利用专门的矩阵乘法加速单元」；mcBLAS、FlashMLA、TileOPs-Metax 均构建在矩阵单元之上

**一处需要留意的表述**：官方文档另一处写「向量指令和矩阵指令由 PEU 执行」，与「矩阵执行单元是独立单元」看似矛盾。最合理的解释是：矩阵执行单元位于 PEU/AP 域内、与向量通路共享 AP 级寄存器堆（mtreg）与指令发射单元，而非完全独立的协处理器。官方未公布矩阵单元的物理布局细节（每 AP 几个、如何与 PEU 分布），❌ 未公布，保留在待核实清单。

### 3.2 显存带宽

**理论带宽（由实测位宽与时钟推算）**：

```
理论带宽 = 位宽 4096 bit ÷ 8 × 双沿 × 时钟 1800 MHz = 512 B × 2 × 1.8 GHz ≈ 1843 GB/s（约 1.8 TiB/s）
```

该推算值与以下来源互相印证：官方性能调优指南记载 C500「DRAM-L2 半双工通路带宽 1.8 TB/s（1843.2 GB/s 量级）」；CSDN 与模力方舟对 C500 的记载同样为 1.8 TB/s。多源一致，可信度较高。⚠️ 3.35 TB/s 的说法（京东商品页，单一来源）与所有其他来源矛盾，存疑。

**实测有效带宽（2026-08-03，本机 STREAM 风格测试）**：

测试代码：`liulian/bench/hbm_bandwidth/hbm_bandwidth.cu`（MUSA C，mxcc 编译），四个 STREAM 内核，带宽口径 = 读 + 写总流量 / 耗时（与 STREAM 惯例一致），取 5 次最佳：

| 内核 | 1 GiB 数组 | 4 GiB 数组 | 说明 |
|---|---|---|---|
| copy | 762 GB/s | 765 GB/s | 读 1 + 写 1 = 2 份流量 |
| scale | 761 GB/s | 765 GB/s | 读 1 + 写 1 = 2 份流量 |
| add | 1154 GB/s | 1162 GB/s | 读 2 + 写 1 = 3 份流量 |
| triad | 1159 GB/s | 1162 GB/s | 读 2 + 写 1 = 3 份流量 |

结果解读：

- **有效带宽约为理论值的 40%–63%**（copy 约 41%、add 约 63%），这是 STREAM 类测试的正常水平——受每线程 4 B 访问粒度、VL1 默认关闭（数据直达 L2）、HBM 读写切换开销等影响
- 大数组（4 GiB）结果与 1 GiB 一致，数据稳定
- 对比：A100 的理论带宽约 2 TB/s（HBM2e 相同），STREAM copy 实测通常为理论值的 60%–75%；C550 的 add/triad（63%）接近该区间，copy（41%）偏低，可能与本机驱动版本（MACA 3.7.1.5）的访存调度有关

如需复现：编译运行方法见测试代码头部注释；测试期间可另开终端用 `mx-smi --show-hbm-bandwidth -l 1000` 观察驱动侧实时吞吐交叉验证。

### 3.3 带宽与算力配比

若按 C500 参照值估算（FP16 280 TFLOPS、带宽 1.8 TB/s），byte/flop 约 6.4，显存带宽相对充裕，有利于大模型训练与推理场景。⚠️ 该估算基于 C500 假设，仅供参考。

#### 带宽口径澄清：896 GB/s 指什么

896 GB/s 是**每张卡对外（到其余 7 张卡）的总双向带宽**（per-GPU aggregate），对标 NVLink 的同类口径，**不是**「两卡之间的带宽」，也**不是**「8 卡相加的系统总带宽」：

- 任意两卡之间只有 1 条直连链路，点对点带宽是**每链路带宽**（128 GB/s 双向 / 64 GB/s 单向），而非 896 GB/s
- 8 卡全互连系统总链路数 = 8 × 7 ÷ 2 = 28 条，系统总双向带宽 = 28 × 128 = 3584 GB/s

与 NVLink 各代对比（同为每卡对外总带宽口径）：

| 代际 | 每链路带宽 | 链路数 / 卡 | 每卡对外总带宽 | 代表产品与拓扑 |
|---|---|---|---|---|
| NVLink 2.0 | 50 GB/s 双向 | 6 | 300 GB/s | V100（DGX-1 全直连） |
| NVLink 3.0 | 50 GB/s 双向 | 12 | 600 GB/s | A100（NVSwitch） |
| NVLink 4.0 | 100 GB/s 双向 | 18 | 900 GB/s | H100（NVSwitch） |
| **MetaXLink** | **128 GB/s 双向** | **7** | **896 GB/s** | **C550（8 卡全直连）** |

架构差异：MetaXLink 与 V100 的 DGX-1 同属「全直连」方案（每对卡独占 1 条链路，无交换机、延迟低）；A100 / H100 每卡全部链路接入 NVSwitch，单对通信共享交换机聚合带宽。两者的 600 / 900 GB/s 与 896 GB/s 口径一致，可直接横向比较。

#### 实测带宽（2026-08-03，容器内 mccl_tests）

| 场景 | 消息大小 | 有效带宽 | 说明 |
|---|---|---|---|
| 2 卡点对点（sendrecv） | 1 GB | 45 GB/s（单向） | 单链路单向理论 64 GB/s 的约 70%，符合高速互连典型利用率 |
| 8 卡 all-reduce | 1 MB | 34 GB/s / 卡 | 小消息：启动开销主导 |
| 8 卡 all-reduce | 64 MB | 135 GB/s / 卡 | — |
| 8 卡 all-reduce | 1 GB | 188 GB/s / 卡（busbw 329 GB/s） | 大消息，多链路并行接近饱和 |

要点：

- **有效带宽约为理论值 70%**：点对点 45 GB/s 对 64 GB/s 单向，与 PCIe / NVLink 的普遍效率区间（70%–85%）一致，协议开销与 ECC 等为正常损耗
- **小消息带宽利用率低**：1 MB 的 all-reduce 每卡仅 34 GB/s，1 GB 能到 188 GB/s，差约 5 倍，通信应尽量合并大消息
- **all-reduce 超过单链路能力**：经典 ring 算法每卡只用收 + 发 2 条链路（约 90 GB/s 上限），实测 188 GB/s 说明 mccl 同时并行使用了多条直连链路，全互连拓扑被充分利用
- 挖掘带宽的方向：大消息合并、多链路分片并行、多流计算通信重叠、按并行策略（TP 高频小消息 / DP 大消息 all-reduce）匹配通信调度

## 调研方法与局限

- 方法：并行检索沐曦官网全部相关产品页，以及 CSDN、知乎、模力方舟、eefocus、同花顺等 20 余个来源；再以本机 `macainfo` / `mx-smi` / `mcGetDeviceProperties` / 自写带宽测试对关键参数做硬件级实测交叉验证。
- 局限：百度 / 360 / 搜狗搜索触发验证码，知乎正文与部分头条文章无法完整抓取，部分媒体信息仅能依据搜索摘要；沐曦官方白皮书未公开，科创板招股书正文未能直接访问；沐曦官方架构文档以 C500 为主（C550 同架构，本机实测数字与官方 C500 文档一致）。
- 结论原则：官网未公布的数字一律标注来源与可信度，不将第三方数据当作官方参数；来源间互相矛盾的数值全部列出并说明差异。
